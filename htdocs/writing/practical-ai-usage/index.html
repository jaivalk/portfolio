practical ai usage: coding with and without ai module 1: the unbreakable foundation (no ai allowed) most people learn to code by typing garbage into an ide and praying it works. if you want to actually build things and not just copy-paste, you need to understand the physics of what's happening under the hood. when you hit run, you're triggering actual physical and logical transformations. 1.1 the mechanics (how the machine actually thinks) your computer speaks electricity (0s and 1s). your code is just an english recipe. - compiled languages (c, rust): it's like a translator taking your whole recipe, translating it to binary, and handing it to the machine. pros: blisteringly fast. cons: one typo and the whole thing stops before it even runs. - interpreted languages (js, python): the translator stands next to the machine and translates line by line on the fly. pros: flexible, fast to test. cons: slower. it might run for 5 minutes and then crash on line 50. why it matters: knowing this stops you from panicking when things break. you know exactly why it stopped. 1.2 the event loop (the waiter) if you write js, you have to know this. imagine a restaurant. the kitchen does the heavy lifting. the waiter is the event loop. if a user clicks a button, the waiter doesn't sit in the kitchen waiting for the steak. that's "blocking" code. the waiter drops the order on the counter (the call stack and task queue), and serves the next person. when the food is done, it gets pushed to the microtask queue (for promises) and brought out. lesson: blocking code is terrible. if you run heavy math on the same line that handles clicks, your site freezes. 1.3 memory (your workbench) code needs space. - the stack: your desk. small, fast, organized. variables live here and die when the function ends. - the heap: the massive warehouse. big objects and arrays go here. the danger: if you throw stuff in the warehouse and never clean it up, you get a memory leak. ai is famous for writing code that leaks memory until the app dies. closures and scope tie into this—if you keep references alive forever, the garbage collector can't clean your mess. module 2: vanilla mastery (the raw materials) modern devs rely on bloated frameworks (react, next.js) and massive libraries (tailwind). they're cool, but they hide the truth. if you want to command ai and build fast, raw sites, you need to cook from scratch. 2.1 the dom and cssom (the puppet strings) html isn't just painted on the screen. the browser builds an invisible, upside-down tree called the dom (document object model). at the same time, it builds the cssom for styles. javascript is the puppeteer. `document.getElementById` reaches into the tree to grab a leaf. if ai writes a messy loop that freezes the screen, it's usually causing too many "reflows" and "repaints"—forcing the browser to redraw the whole screen on every frame. you have to know which leaf is burning. event delegation is key here too—don't put an event listener on 1000 buttons, put it on their parent. 2.2 native apis (the free toolbox) the browser gives you crazy tools for free. you don't need third-party bloated libraries for everything. - need to fetch a db? use native `fetch()`. - need to save state? `localStorage` or `sessionStorage` (how i fake my spa transitions). - real-time stuff? native `WebSockets`. ai will always try to import some npm package for simple math. delete it, and tell the ai: "rewrite this using only native browser apis." 2.3 state (the brain's memory) state is just "how things are right now". is the user logged in? what's the theme color? frameworks do magic where changing a variable updates the screen. in vanilla, you wire it yourself. change the state, then manually tell the dom to update. it's raw, but you control every pixel. module 3: data structures & logic ai just wants to output an answer. it doesn't care if the computer burns cpu cycles to get it. 3.1 the containers - arrays (the bookshelf): ordered lists. great if order matters. flaw: finding something means checking every single spot. - hash maps (the filing cabinet): in js, an object or map. superpower: looking up an item is instant. no searching, just grabbing. 3.2 big-o notation (the speed limit) - o(1) constant time: the holy grail. takes the same time no matter what. hash map lookups are o(1). - o(n) linear time: standard stuff. searching an array start to finish. - o(n^2) quadratic time: the danger zone. a loop inside a loop. ai loves writing this garbage. the fix: don't just ask ai for an answer. tell it: "turn list a into a hash map for instant lookups. loop list b once and check it against the map." boom. you just turned an o(n^2) slog into a blisteringly fast o(n) operation. module 4: the manual debugger (when ai fails) ai will eventually enter a death loop where it loses context and just guesses blindly. you need to know how to hunt bugs yourself. 4.1 trace reading a stack trace is just history. read the top line to see what broke (like `TypeError`). ignore framework or node_modules garbage. find the top line that points to *your* file. that's where the fire is. 4.2 native tools (the scalpel) use `debugger;`. drop it in your code, open devtools, and time freezes. watch the variables change frame by frame until you catch the exact moment it breaks. console logs are for beginners; the debugger is the scalpel. 4.3 the isolation method if there's no trace, divide and conquer. cut the system in half. check the network tab: did the backend fail, or the frontend? put a debugger at the top of your render function. if the data is there, the bug is trapped in those 5 lines of render code. paste *only those 5 lines* to ai. module 5: ai as your co-pilot 5.1 prompting for system design (c.a.s.t.) ai will hallucinate if you don't box it in. - context: "i'm building a vanilla js site. no frameworks." - architecture: "filter 5k objects. debounce the input by 300ms so we don't fry the browser." - strict constraints: "no external libraries. no css. just the js function." - target output: "only raw js code. zero explanations." 5.2 context scoping (the sniper) don't do data dumps. ai's attention span is terrible. - isolate the 10-20 lines that are broken. - provide inputs/outputs. - delete everything that doesn't manipulate the broken data before giving it to ai. 5.3 the boilerplate generator ai is perfect for code that takes zero creativity. config files, crud routes, unit tests, jwts scaffolding. let it write the boring stuff. but the rule stands: read every single line. if you don't understand it, delete it. module 6: code auditing (the human check) 6.1 spotting hallucinations ai will invent perfect-sounding methods that don't exist (like `myArray.unique()`). or give you python syntax in a js file. use your ide. if it says `any` or there are no docs, stop. search mdn. 6.2 security audits ai is trained on public github repos, meaning it learned from terrible developers too. - injection flaws: ai will concatenate sql strings. force it to use parameterized queries. - exposed secrets: ai will hardcode api keys. prompt it to use env vars. - xss: ai will render user input directly. always make it sanitize first. module 7: the practical workflow 7.1 the decision matrix context (isolated vs coupled) and risk (cosmetic vs business logic). - zone 1 (low context, low risk): css, boilerplate. fully automate. - zone 2 (low context, high risk): security/auth (like jwts). prompt strictly, audit aggressively. - zone 3 (high context, low risk): write the skeletons yourself, let ai fill the dom manipulation. - zone 4 (high context, high risk): core system architecture. turn off the ai. grab a whiteboard. write the logic yourself. 7.2 interview prep interviews are tricky. they don't want prompt monkeys, but they don't want dinosaurs either. the trap question: "i use ai aggressively for boilerplate and unit tests, but strictly turn it off for core architecture and state management. if i don't own the vanilla logic, i spend more time debugging ai hallucinations than actually coding." when you screen-share, explain your architecture first. then prompt the ai, and audit the output out loud before you paste it. you are driving the machine, not the other way around. having the taste to know when a design is actually good, or the guts to just delete a whole section because it feels off? that’s all you.
